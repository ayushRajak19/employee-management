1. Executive Summary

1.1 Product Definition

MobiusEMS is the flagship workforce-intelligence, human capital management, and commercial operations platform developed by Mobius Bloom Venture Pvt Ltd. Engineered as an autonomous Node.js service mapped to employee.whalexy.com, it is strictly decoupled from the legacy PHP/Laravel application at whalexy.com. Its architectural boundary extends beyond traditional HR records into verified capability intelligence, Kanban work delivery, explainable performance evaluation, geofenced mobile attendance, recruiting automation, commercial sales GIS mapping, and zero-retention advisory AI.

1.2 What the Platform Currently Covers

  • Identity & Access: Cookie-based JWT sessions, rotating refresh tokens with token family replay protection, forced credential rotation, resumable onboarding, and granular database-backed RBAC.
  • Workforce Structure: Organization trees, departments, teams, designations, reporting managers, and Employee 360 longitudinal profiles.
  • Capability Intelligence: Standardized skill directories, employee claims, immutable verification audit trails, timed assessments, and departmental capability heatmaps.
  • Execution & Work Delivery: Projects, Kanban board with validated state transitions, blocker root-cause logging, append-only activity history, and local voice-to-task commands.
  • Deterministic Outcomes: Goals, KPIs, 360 reviews, and frozen performance snapshots with explainable mathematical weighting.
  • Commercial Sales & GIS: Hierarchical geographic trees (Global-to-Area), territory allocations, lead lifecycles, opportunity pipelines, and automated revenue booking.
  • Operational Workflows: Haversine geofenced mobile attendance, weekly contribution scoring, Brevo email automation, and private employee to-do checklists.
  • Advisory AI: Multi-provider LLM gateway with strict policy guardrails prohibiting autonomous employment decisions.

Core Architectural Tenets

1. Deterministic Scoring

All KPI math, performance ratings, contribution percentiles, attendance determinations, and sales capacity gaps are computed via deterministic TypeScript formulas. LLMs are never permitted to generate quantitative outcomes.

2. Advisory AI Boundary

AI operates strictly as an assistive drafting tool. System policy and application code strictly prohibit AI from executing binding employment actions (promotions, salary revisions, disciplinary actions, or terminations).

3. Fail-Closed Tenancy

Data access requires active tenant context established from verified JWT sessions. Invocations without tenant context fail closed at the Mongoose proxy level, preventing cross-tenant data exposure.

4. Zero-Retention Voice Privacy

Audio commands are transcribed on-host via faster-whisper and destroyed immediately in a finally block. No audio is ever persisted to object storage or database records.

2. Scope, Objectives and Boundaries

2.1 Business Objective

MobiusEMS centralizes organizational operations, workforce capability, delivery tracking, and commercial pipeline management into a single auditable platform. It replaces disparate point solutions while maintaining explainable evidence layers that empower managers without delegating sensitive decisions to opaque AI models.

2.2 Architectural Boundaries

  • Independent Runtime: Complete decoupling from legacy PHP/Laravel at whalexy.com.
  • REST API Gateway: Express owns /api/v1/* and serves the compiled React 19 SPA.
  • Encapsulated Business Rules: Business logic lives in services; routes compose validation and auth guards.
  • Bounded History: Growing historical data (audit logs, task activities, snapshots) resides in dedicated collections.

7. Data Architecture and Persistence

7.1 Database Strategy

MongoDB Atlas is the primary persistence layer. All business collections strictly enforce immutable tenantId scoping, soft-deletion timestamps (isActive, archivedAt, deletedAt), and explicit Zod field allowlists. Uniqueness and lookup indexes lead with tenantId to guarantee tenant-level uniqueness and rapid query execution. Historical records (audit logs, task activities, performance snapshots) are stored in dedicated collections to prevent unbounded document growth.

8. Multi-Tenancy and Isolation

MobiusEMS implements a logical multi-tenancy model backed by a central, fail-closed Mongoose model wrapper and Node.js AsyncLocalStorage execution context derived from verified JWT access tokens.

1. Verified Session

2. Async Context

• Auto-injects tenantId

• Compound unique indexes

Figure 2. Fail-closed multi-tenancy model enforced across all query and mutation paths.

8.1 Required Tenancy Invariants

  • Strict Context Binding: Every tenant-owned business record must carry an immutable tenantId.
  • Client Independence: Database queries never rely on the client supplying tenantId; it is exclusively extracted from verified session credentials.
  • IDOR Immunity: Lookups by raw MongoDB _id cannot leak cross-tenant records because all Mongoose queries automatically enforce { _id, tenantId }.
  • Aggregation Scoping: Aggregation pipelines automatically receive a $match: { tenantId } as Stage 0.
  • Platform Segregation: Platform tenant administration endpoints (/api/v1/platform/*) are strictly restricted to the Super Admin role and allowlisted emails in PLATFORM_ADMIN_EMAILS.
Enterprise Release Gate: Multi-Tenant Negative Testing

Multi-tenant isolation is protected by automated tests in tenantModel.test.ts that actively attempt cross-tenant reads, writes, batch inserts, and aggregations without context, verifying that every operation fails closed.

9. Authentication, Authorization and Security

9.1 Authentication Model

MobiusEMS utilizes a dual-token cookie pattern. The access token (15-minute lifespan) and refresh token (7-day lifespan) are stored in HttpOnly, Secure, SameSite=Strict cookies. Passwords are salted and hashed using bcrypt. Refresh tokens rotate upon renewal, and reuse of a previously invalidated refresh token triggers immediate revocation of the entire session family.

12. Attendance, People Operations and Automation

12.1 Attendance Engine & Geofencing Rules

The attendance system (attendanceService.ts) enforces precise mathematical rules:

  • Haversine Spherical Distance: Validates user coordinates against configured office location (Default: Shivnath Business Centre, Raipur; Lat: 21.251413, Lon: 81.709438). Permitted geofence radius: ≤ 300 meters.
  • GPS Anti-Spoofing Gate: Mobile coordinates with device accuracy > 200 meters are rejected with HTTP 422.
  • IST Timezone & Shift Cutoffs: Evaluated in Asia/Kolkata. Check-in after 11:30 AM IST automatically classifies daily status as LATE; otherwise PRESENT.
  • Checkout Duration Check: Check-out calculates worked minutes. Durations < 240 minutes (4 hours) demote status to HALF_DAY.
  • Organization Register: Super Admin view classifies daily workforce into PRESENT, LATE, HALF_DAY, ON_LEAVE, or ABSENT.

12.2 Talent Acquisition & Resume Screening

Recruiting components manage job requisitions and candidate pipelines. Server-side libraries (pdf-parse, mammoth) extract text from uploaded resumes. The screening service extracts skills, experience, and education, generating an assistive match score. Final hiring decisions remain human-driven.

12.3 Email Automation Architecture

The email automation engine (emailAutomationService.ts) manages multi-step lifecycle drip campaigns:

  • Dual Gateway: Primary transactional delivery via Brevo API with webhook tracking; Nodemailer SMTP fallback.
  • Workflow State: Step delays, dynamic token replacement, and enrollment status tracking.
  • Safety Throttle: Enforces a strict 250 emails/day cap (EMAIL_AUTOMATION_DAILY_LIMIT) to prevent domain blacklisting.

12.4 Daily Todos (Personal Productivity)

13. Commercial Sales Intelligence & Spatial GIS

The Commercial Sales Intelligence subsystem bridges human capital management with revenue operations, providing end-to-end sales lifecycle tracking, territory alignment, and geospatial workforce mapping.

13.1 Canonical GIS Hierarchy (GeoNode)

Geographic intelligence is structured into a canonical, self-referencing tree model (GeoNode): GLOBAL → COUNTRY → STATE → DISTRICT → CITY → AREA → PINCODE. GeoNodes store geospatial coordinates and boundary polygons, decoupled from dynamic sales territories.

13.2 Sales Territories & 3-Tier Scoping

  • Dynamic Boundaries: SalesTerritory groups multiple GeoNodes under commercial ownership.
  • Staff Allocation: EmployeeTerritoryAssignment manages effective-dated rep allocations.
  • 3-Tier ABAC Scoping: salesScopeService.ts dynamically evaluates actor permissions:
    • SELF: Sales rep views only self-owned leads, pipeline, targets, and revenue.
    • TEAM: Sales manager views self plus all direct/indirect reporting team members in assigned territories.
    • ALL: HR Admin receives tenant-wide read-only visibility; Super Admin receives mutation rights.

13.3 Lead Lifecycle & Automated Revenue Booking

Leads move through NEW → CONTACTED → QUALIFIED → CONVERTED / LOST. Marking a lead as CONVERTED automatically provisions a linked SalesCustomer. Commercial deals are tracked through SalesOpportunity. Moving an opportunity to WON automatically generates an audited SalesRevenueTransaction and increments customer lifetime revenue idempotently.

19. Performance and Scalability Considerations

  • Host Co-location: Serving static SPA, API, and local Whisper on one host creates a shared scaling boundary. Whisper memory usage must be monitored under load.
  • Atlas Connection Pooling: Configured via MONGODB_MIN_POOL_SIZE=2 and MONGODB_MAX_POOL_SIZE=30 to prevent connection exhaustion.
  • External Latency Shielding: AI inference calls use strict abort timeouts (45s) and low temperatures (0.2) to limit execution duration.
  • Stateless Horizontal Scaling Path: The Node application is stateless; future load growth can scale horizontally behind a load balancer with Redis session caching.
